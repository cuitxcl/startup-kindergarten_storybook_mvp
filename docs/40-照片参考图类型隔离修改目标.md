# 照片参考图类型隔离修改目标

> 使用场景：后续实现“添加什么类型的图片，就生成什么类型的参考图”，并避免人物照片中的背景被误用到绘本生成中。

## Problem

当前专属绘本创作已经支持把上传照片标记为人物、玩具/物品/宠物、场景，并生成同画风视觉参考。但参考图生成提示词和后续生成输入仍偏通用：

- 人物照片可能包含房间、墙面、桌椅等背景，生成人物参考图时容易把背景一起绘入参考图。
- 从已有绘本定制时，已确认照片参考会被整体挂到个性化/重绘页面，人物、道具、场景参考没有在页面输入中明确隔离。
- 后续插图生成如果只读取混合的 `asset_reference_ids` / `confirmed_photo_references`，可能把场景参考当成人物上下文，或把人物照片背景当成故事场景。

一句话目标：**照片类型必须决定参考图类型和后续使用方式，人物参考只服务角色一致性，场景参考只服务背景/地点，道具参考只服务物品/宠物元素。**

## Target user

- 幼儿园老师：上传孩子、家人、玩具、教室或幼儿园照片，用来制作专属绘本。
- 园所管理员：需要创作流程可恢复、可解释，且生成结果稳定可控。

## Goal

1. 用户选择“人物”上传照片时，只生成角色设定参考图，弱化或移除原照片背景。
2. 用户选择“玩具/物品/宠物”上传照片时，只生成道具/宠物设定参考图，不生成完整场景。
3. 用户选择“场景”上传照片时，生成场景/背景参考图，不把它绑定为角色参考。
4. 最终绘本生成输入中，人物、道具、场景参考必须按类型分组或按页面用途隔离。
5. 保留现有“生成参考、确认参考、重新生成、不使用、移除”的交互闭环。

一期目标只保证用户选择的照片类型被严格贯彻到参考图生成和最终生成输入中，不追求自动识别照片内容。

## Non-goals

- 不重做照片上传、鉴权、预览和撤销机制。
- 不引入新图片生成供应商。
- 不把真实照片直接贴进绘本插图。
- 不在本阶段实现自动识别图片类型；类型仍由老师上传前选择。
- 不处理复杂的多人物自动抠图和主体分割，只通过提示词和生成输入约束降低背景污染。
- 不在本阶段支持宠物作为独立角色类型；宠物暂按 `object` / `prop_reference` 处理。

## User flow

1. 老师在照片素材区选择照片类型：人物、玩具/物品/宠物、场景。
2. 老师点击添加照片并上传。
3. 系统保存资产引用时记录 `kind`。
4. 老师填写名称并确认用途。
5. 系统按 `kind + usage` 生成对应类型的视觉参考：
   - 人物：角色参考图。
   - 物品/宠物：道具参考图；宠物一期也按道具参考处理。
   - 场景：场景参考图。
6. 老师确认参考图后，该参考才进入故事计划和最终制作输入。
7. 生成故事方向、变化计划或最终绘本时，系统按类型使用参考图，避免混用。

## Data implications

现有数据字段已经具备基础：

- `storybook_asset_references.kind`：`person` / `object` / `scene`
- `storybook_asset_references.usage`：`main_character` / `story_friend` / `story_object` / `background_scene` / `name_only` / `unused`
- `storybook_visual_references`：保存同画风视觉参考任务和确认状态

建议补充或在生成输入中派生以下字段：

- `reference_type`
  - `character_reference`
  - `prop_reference`
  - `scene_reference`
- `generation_constraints`
  - 人物参考：`neutral_background`、`ignore_source_background`
  - 道具参考：`isolated_prop_reference`
  - 场景参考：`background_scene_reference`

数据库层可不新增字段，优先在后端组装 generation input 时派生，降低迁移成本。

## API implications

现有接口基本可复用：

- 上传资产：继续接收 `kind`
- 更新用途：继续校验 `kind + usage`
- 生成视觉参考：内部按 `kind + usage` 组装不同 prompt
- 确认视觉参考：继续使用现有确认接口

需要调整的响应或生成输入：

1. `generate_visual_reference` 的 job input 增加 `reference_type`。
2. `confirmed_photo_references` 中保留 `kind`、`usage`、`reference_type`。
3. 最终生成 input 增加类型分组：
   - `character_photo_references`
   - `prop_photo_references`
   - `scene_photo_references`
4. 页面计划中不要只放混合 `asset_reference_ids`，应补充：
   - `character_reference_ids`
   - `prop_reference_ids`
   - `scene_reference_ids`

## UI implications

前端现有分段控件可以保留，但需要让状态文案更贴合类型：

- 人物：`生成角色参考`、`确认角色参考`
- 玩具/物品/宠物：`生成道具参考`、`确认道具参考`
- 场景：`生成场景参考`、`确认场景参考`

确认参考区域应继续展示生成出的同画风参考图。无需增加复杂设置项。

## Functional requirements

1. 上传照片时必须保存用户选择的 `kind`。
2. `person` 只能选择人物相关用途：`main_character`、`story_friend`、`name_only`、`unused`。
3. `object` 只能选择 `story_object` 或 `unused`。
4. `scene` 只能选择 `background_scene` 或 `unused`。
5. `name_only` 不需要生成视觉参考。
6. 除 `name_only` 和 `unused` 外，所有会进入绘本生成的照片必须先生成并确认视觉参考。
7. 人物视觉参考 prompt 必须明确要求：
   - 保留人物主体关键特征。
   - 不沿用原照片背景作为故事场景。
   - 使用纯色、留白或简洁中性背景。
   - 输出为角色设定参考，而非完整插图。
8. 道具视觉参考 prompt 必须明确要求：
   - 保留物品/宠物主体特征。
   - 不生成复杂场景。
   - 输出为道具/宠物设定参考。
   - 宠物一期不作为角色一致性参考绑定到 `storybook_roles`。
9. 场景视觉参考 prompt 必须明确要求：
   - 保留地点、空间、色彩和环境特征。
   - 输出为绘本背景/地点参考。
   - 不把照片中的人物作为角色主体。
10. 从已有绘本定制时，不得把全部已确认参考无差别挂到每个重绘页面。
11. 直接创作和来源书定制的最终 generation input 都必须能区分人物、道具、场景参考。
12. 场景参考不默认套用到所有个性化/重绘页面，只能进入明确需要该地点或背景的页面；如果暂时无法判断页面地点，则作为全局场景候选进入 plan，不进入页级 `scene_reference_ids`。

## Constraints

- 继续使用当前 Rust 后端、SeaORM/PostgreSQL、React 前端。
- 继续使用现有 Seedream 图片生成 provider。
- 不破坏已有 session 恢复能力。
- 不降低现有生成门禁：未确认视觉参考不能开始最终制作。
- 不提交或依赖真实儿童照片作为测试资产。

## Phase 1 scope

P0 必须完成：

1. 修改 `server/src/application/storybook_creation_assets.rs`
   - 将 `visual_reference_generation_input` 改为按 `kind` 生成不同 prompt。
   - 在 job input 中增加 `reference_type`。
   - 为人物参考增加“忽略原照片背景”的强约束。

2. 修改 `server/src/application/storybook_customization.rs`
   - 调整 `attach_photo_references_to_page_plan`。
   - 不再把所有参考统一塞到 `asset_reference_ids`。
   - 按 `kind` 生成 `character_reference_ids`、`prop_reference_ids`、`scene_reference_ids`。
   - 场景参考仅在页面计划明确需要该地点/背景时进入页级 `scene_reference_ids`；无法判断时只进入全局候选字段。
   - `confirmed_photo_reference_json` 保留并标准化 `reference_type`。

3. 检查 `server/src/application/storybook_creation.rs`
   - 直接创作 input 中保留 `asset_references`。
   - 补充按类型分组字段，便于生成 worker 和 prompt 消费。
   - 确保只有 `person` 被绑定到角色参考图。

4. 补充测试
   - 覆盖三类 prompt。
   - 覆盖定制页面计划按类型分组。
   - 覆盖 `name_only` 不需要视觉参考。
   - 覆盖场景参考不会默认进入所有重绘页。

P1 可跟随完成，但不阻塞 P0：

1. 修改前端文案
   - 将“同画风参考”在具体照片卡片中替换为更具体的“角色参考/道具参考/场景参考”。
   - 在人物参考确认区提示人物照片背景不会作为故事场景使用。

## Later phases

- 自动检测上传图片类型并提醒用户类型不匹配。
- 人物参考图增加自动主体裁切或背景移除。
- 支持一张照片中多个人物的手动选择。
- 支持宠物角色类型，例如 `pet_character` / `pet_reference`，并明确何时绑定到角色一致性链路。
- 在前端展示“这张参考将作为角色/道具/场景使用”的可视化说明。
- 在生成结果审计中展示每页实际使用了哪些类型的参考。

## Acceptance criteria

1. 上传人物照片并选择“主角”后，生成视觉参考任务 input 的 `reference_type` 为 `character_reference`。
2. 人物视觉参考 prompt 包含“不要沿用原照片背景”或等价约束。
3. 上传场景照片并选择“用作故事场景”后，生成视觉参考任务 input 的 `reference_type` 为 `scene_reference`。
4. 场景视觉参考 prompt 不要求生成角色设定。
5. 上传物品照片并选择“把它写进故事”后，生成视觉参考任务 input 的 `reference_type` 为 `prop_reference`。
6. `name_only` 用途不会触发视觉参考生成，也不会阻塞最终制作。
7. 从已有绘本定制生成变化计划时，页面计划中人物、道具、场景参考 ID 被分到不同字段。
8. 页面计划中不存在把所有确认参考无差别复制到每个重绘页的行为。
9. 直接创作最终 generation input 中能读取到按类型分组的照片参考。
10. 未确认、失败、撤销或不使用的照片不会进入最终 generation input。
11. 场景参考不会默认出现在所有个性化/重绘页的 `scene_reference_ids` 中；没有明确页面落点时，只作为全局场景候选保留。
12. 宠物照片在一期生成 `prop_reference`，不会绑定为角色参考图。

## Open questions

1. 页面计划如何判断“明确需要该场景”：通过素材名称匹配、用户选择、还是生成计划返回？
2. 人物参考图是否需要固定为半身/全身角色设定，还是允许模型自行决定？
3. P1 前端提示是否需要出现在确认前，还是只在生成结果解释中展示？

## Risks and assumptions

- 仅靠 prompt 不能百分百消除人物照片背景影响，但可以显著降低混入概率。
- 如果图片生成 provider 对 `edit_instruction` 或 `strength` 的遵循不稳定，可能仍需要后续加入主体裁切或背景移除。
- 当前后端测试可以验证 input 和 prompt 结构，但真实生成效果仍需要人工抽样验收。
- 第一版假设用户上传前选择的照片类型可信，不做自动纠错。
- 第一版假设宠物按道具处理可以满足多数低风险场景；如果用户希望宠物像主角一样贯穿全书，需要后续扩展宠物角色链路。
