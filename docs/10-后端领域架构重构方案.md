# 后端领域架构重构方案

## 当前问题

`server/src/controllers/api.rs` 已经承担了过多职责：路由注册、请求解析、权限校验、领域流程、mock 分支、数据库分支、审计日志、导出下载、公开链接、运营后台和 readiness 检查都集中在一个文件中。当前文件超过 5000 行，继续新增功能会带来三个问题：

- 修改一个领域时容易影响其他领域。
- 权限、错误处理、审计日志等横切逻辑难以复用。
- Loco 的 controller/service/repository 分层优势没有发挥出来。

后端下一步不应继续在 `api.rs` 中追加业务，而应先做领域化拆分。

第一阶段保持现有 API 路径和返回结构不变，只调整代码组织。

## 当前落地状态

截至当前版本，旧的巨型 `controllers/api.rs` 已不再作为业务入口，后端已经形成 Loco 风格的领域分层：

- `server/src/controllers/`：按 `auth`、`workspaces`、`organization`、`children`、`storybooks`、`generation`、`delivery`、`marketplace`、`submissions`、`operator` 等领域拆分路由和 handler。
- `server/src/application/`：按领域承接用户用例编排，包括普通绘本、定制绘本、市场复制、投稿隐私确认、分享导出、生成任务恢复等流程。运营端 readiness 已从 `operator.rs` 拆到 `operator_readiness.rs`，把试点前检查编排从普通运营列表/审核操作中分离；readiness 的数据库结构、provider 配置、密钥、APP_HOST、token TTL、预算和演示数据开关等具体检查规则已进一步拆到 `operator_readiness_checks.rs`，让 readiness 用例入口不再承担所有校验细节；定制绘本单个/批量派生已从 `storybooks.rs` 拆到 `storybook_customization.rs`，让普通绘本编辑和儿童定制派生的应用层职责分开；绘本分页编辑和角色编辑已从 `storybooks.rs` 拆到 `storybook_editing.rs`，输入清洗、老师复核状态校验和状态/可见性名称映射已拆到 `storybook_inputs.rs`，让普通绘本主用例、编辑用例和输入规则分离；生成图片下载、文件名安全校验和图片 URL 重写已从 `generation.rs` 拆到 `generation_image_access.rs`，让生成任务编排和生成产物访问分离；生成任务重试、取消和队列恢复已从 `generation.rs` 拆到 `generation_job_actions.rs`，让任务创建/查询和任务状态操作分离。
- `server/src/repositories/`：承接 PostgreSQL/SeaORM 读写、分页、状态更新和持久化查询。生成成本和预算已从 `generation.rs` 拆到 `generation_costs.rs`，图片任务输入和目标解析已拆到 `generation_image_tasks.rs`，生成任务入队、查询、分页、领取、完成、失败、取消和超时重排已拆到 `generation_jobs.rs`，生成结果写回绘本角色/分页/角色参考图的逻辑已拆到 `generation_writeback.rs`，空间存储限额已拆到 `storage_quota.rs`，绘本状态机、可交付校验和角色视觉变更规则已拆到 `storybook_rules.rs`，单儿童定制绘本派生已拆到 `storybook_customization.rs`，页面和角色编辑 SQL 已拆到 `storybook_editing.rs`，绘本列表/详情查询已拆到 `storybook_queries.rs`，普通绘本创建、市场模板复制、绘本副本和页面角色克隆已拆到 `storybook_factory.rs`，市场模板列表/详情/编辑已从 `market.rs` 拆到 `market_templates.rs`，园所投稿列表、创建、隐私确认、审核上架和驳回已从 `market.rs` 拆到 `market_submissions.rs`，市场投稿状态过滤、投稿行映射和投稿转市场模板已拆到 `market_submission_helpers.rs`，导出分享和市场投稿共用的儿童隐私风险扫描已拆到 `privacy.rs`，让任务编排、任务表状态、成本账本、容量控制、生成写回、绘本规则、定制策略、编辑行为、读取查询、创建复制、市场模板、市场投稿和隐私检查各自收敛。
- `server/src/domains/common/`：沉淀 token、workspace 权限、班级授权、分页、通用错误映射等横切规则。
- `server/src/services/`：承接底层生成 provider、PDF、storage。生成 provider 已进一步拆出 `generation_provider_contract.rs`，把跨层请求、错误、图片参考和 provider 摘要类型从具体 DeepSeek/Seedream/mock 实现中分离；新增 `generation_privacy.rs`，集中处理外发 provider 输入脱敏、图片 prompt 脱敏、隐私审计标签和 provider 输出内容安全扫描；新增 `generation_output_validator.rs`，集中处理 provider 输出 envelope 补齐和按任务类型校验 `plan/roles/pages/customization` 结构；新增 `generation_mock_provider.rs`，承接本地 mock 文本结果、mock 插图占位图和演示生成内容；新增 `generation_deepseek_provider.rs`，承接 DeepSeek 文本生成、prompt/schema 契约、JSON mode payload、真实 HTTP 响应解析和文本任务 summary；新增 `generation_seedream_provider.rs`，承接 Seedream 图片生成、参考图/编辑图 payload、图片响应解析、PNG 校验和本地图片写入；新增 `generation_provider_config.rs`，集中处理 provider 环境变量、默认值和错误截断 helper；新增 `generation_provider_summary.rs`，集中生成运营后台和 workspace readiness 需要的 provider summary、组件状态、缺失配置和诊断文案；新增 `generation_provider_tests.rs`，把 provider 编排、DeepSeek、Seedream、隐私脱敏和输出校验测试从门面文件迁出。当前 `generation_provider.rs` 已压缩为约 150 行的 provider 编排门面。PDF 已新增 `pdf_images.rs`，把 PNG 解码、RGB 转换和插图等比适配从 PDF 对象编码中拆出；`pdf.rs` 继续保留绘本 PDF 页面组织、对象编码和可搜索文本标记。storage 已新增 `storage_quota_summary.rs`，把用户个人容量、个人空间容量、园所空间容量、预警线和容量摘要计算从本地文件读写中拆出；`storage.rs` 继续作为兼容门面和本地 PDF/PNG 文件存储实现，保留原有 `crate::services::storage::*` 调用方式。

后续重构重点不再是“从 `api.rs` 拆 controller”，而是继续把超大领域实现拆成更细的 domain/service 文件，尤其是生成 repository、故事绘本 repository 和运营 readiness。

## 分层职责

重构后建议采用 `controller -> application -> domain/service -> repository` 的方向，而不是让 controller 直接编排所有业务。

| 层 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| Controller | 路由、请求体解析、Path/Query/Header 提取、HTTP 状态码、返回 envelope | 复杂业务编排、跨表事务、领域规则 |
| Application | 一个用户用例的完整编排，例如“创建普通绘本”“批量生成定制绘本”“复制市场模板”“确认投稿隐私” | SQL 细节、HTTP 细节、底层 provider 调用细节 |
| Domain / Service | 领域规则、状态机、生成策略、隐私检测、可导出规则、权限语义 | 请求解析、数据库 CRUD |
| Repository | 数据库读写、查询条件、事务内持久化 | 业务流程决策 |
| Worker / Task | 异步执行、重试、任务状态推进 | 同步 HTTP 入口决策 |

`application` 层的价值是把“一个按钮背后的完整业务动作”收束到明确用例里。否则 controller 拆成多个文件后，复杂流程仍然会散落在各个 handler 中，只是从一个大文件变成多个中等文件。

## 领域边界

| 领域 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| Auth | 登录、注册、当前用户、邀请接受、token 解析 | workspace 内权限策略 |
| Workspaces | 空间列表、空间上下文、dashboard 汇总 | 成员管理细节 |
| Organization | 园所成员、班级、审计日志 | 儿童档案内容 |
| Children | 儿童档案 CRUD、归档恢复、老师班级可见范围 | 定制绘本生成 |
| Parent Intakes | 家长资料收集链接、公开提交、确认入档 | 分享绘本 |
| Storybooks | 普通绘本、定制绘本、页面、角色、复制、批量定制派生 | AI 任务执行 |
| Generation | 生成任务、重试、取消、恢复、图片下载 | 具体绘本 CRUD |
| Delivery | 导出任务、分享链接、公开导出下载 | 市场投稿 |
| Marketplace | 市场模板列表、详情、复制 | 园所投稿审核流 |
| Submissions | 园所投稿、隐私确认 | 平台运营审核 |
| Operator | 平台审核、成本、存储、readiness | 园所日常工作流 |
| Public Links | 不登录访问的分享链接、家长资料链接解析 | 登录态空间能力 |

## 横切能力抽取

这些逻辑不应继续散落在各 controller 中：

- `auth_context`：解析 bearer token、当前用户、dev token。
- `workspace_guard`：`workspace member / editor / admin / operator` 权限。
- `classroom_scope`：`school_teacher` 的班级儿童范围。
- `api_error_map`：数据库错误到业务错误的转换。
- `audit_events`：审计事件名称和 payload 构造。
- `delivery_guard`：可导出、可分享、隐私风险拦截。
- `pagination`：分页参数、分页响应。
- `readiness`：试用环境检查，与业务 controller 分离。

建议目录：

```text
server/src/domains/common/
  auth_context.rs
  workspace_guard.rs
  classroom_scope.rs
  error_map.rs
  audit_events.rs
  pagination.rs
```

## 迁移顺序

### 第 1 步：路由聚合拆分

新增 `controllers/routes.rs`，由它聚合各领域 routes：

```rust
pub fn routes() -> Routes {
    Routes::new()
        .merge(health::routes())
        .merge(auth::routes())
        .merge(workspaces::routes())
        .merge(children::routes())
        .merge(storybooks::routes())
}
```

验收标准：`cargo run -- routes` 中路径不变。

### 第 2 步：抽出 application 用例入口

先不要把所有逻辑塞进新的 controller 文件。每迁移一个领域时同步创建对应 application 模块：

```text
server/src/application/storybooks/
  mod.rs
  create_plain.rs
  derive_custom.rs
  derive_custom_batch.rs
  update_page.rs
```

controller 只负责调用 application：

```rust
let output = storybooks::derive_custom_batch::execute(&ctx, actor, workspace_id, storybook_id, input).await?;
Ok((StatusCode::CREATED, Json(Envelope::new(output))))
```

验收标准：新 controller 文件不再直接包含大量 repository 调用、审计 payload 拼装和跨领域权限判断。

### 第 3 步：先拆低耦合 controller

优先迁移：

- `health`
- `auth`
- `workspaces`
- `organization`
- `children`

这些领域对生成、导出、市场的依赖较少，适合先拆。

### 第 4 步：拆故事与生成领域

迁移：

- `storybooks`
- `generation`
- `delivery`

这里需要先抽出 `workspace_guard`、`classroom_scope`、`delivery_guard`，否则只是把大文件拆成多个相互复制的小文件。

### 第 5 步：拆市场、投稿、运营后台

迁移：

- `marketplace`
- `submissions`
- `operator`
- `public_links`

这一步完成后，旧 `controllers/api.rs` 应删除，或只保留兼容入口。

## 阶段一冻结原则

- 不改 URL。
- 不改 envelope：成功 `{ data }`，失败 `{ error }`。
- 不改数据库表。
- 不重写 repository。
- 不新增生产化能力。
- 每迁移一个领域就跑一次 `cargo fmt && cargo test`。

## 优先拆分清单

| 优先级 | 文件/模块 | 原因 |
| --- | --- | --- |
| P0 | `controllers/routes.rs` | 先建立领域路由入口，后续迁移不影响 App 注册 |
| P0 | `application/mod.rs` | 建立用例层，避免新 controller 继续变胖 |
| P0 | `domains/common/workspace_guard.rs` | 权限校验是所有 workspace API 的共同依赖 |
| P0 | `controllers/health.rs` | 最低风险，用于验证拆分方式 |
| P0 | `controllers/auth.rs` | 登录注册相对独立 |
| P1 | `controllers/children.rs` | 真实试用高频，且边界清晰 |
| P1 | `controllers/storybooks.rs` | 产品核心，但体量较大，放在 common 抽取之后 |
| P1 | `controllers/generation.rs` | 与 worker/provider 强相关，应独立 |
| P2 | `controllers/operator.rs` | 运营后台体量大，但不影响老师主路径 |
