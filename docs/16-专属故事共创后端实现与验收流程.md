# 专属故事共创后端实现与验收流程

## 1. 文档定位

本文档用于指导“专属故事共创”后端能力的实现协作和验收。

它承接：

- `14-专属故事共创创建流程UI执行方案.md`
- `15-专属故事共创后端接口契约.md`
- `17-资深产品视角下的绘本创作流程理解.md`
- `03-后端接口契约.md`
- `05-异步任务与生成队列设计.md`

目标是让 5 个设计 skill 按固定顺序协作，避免数据库、状态机、API、异步任务和前端流程各自正确但整体不通。

## 2. 总体协作流程

```text
冻结输入文档
  -> database-schema-design
  -> workflow-state-machine-design
  -> api-contract-design
  -> job-queue-design
  -> full-stack-design-sync
  -> 后端实现
  -> 三层验收
  -> 前端接入与最终复验
```

核心原则：

- 先设计数据，再设计状态。
- 先锁接口，再实现异步任务。
- 先理解产品北极星，再判断实现是否正确。
- 最后由 full-stack-design-sync 做跨层一致性验收。
- 每一步都要产出可检查文档或清单，不只给口头结论。

## 3. 冻结输入

开始实现前，先冻结以下输入。

| 文档 | 用途 |

| `14-专属故事共创创建流程UI执行方案.md` | 定义用户 5 步流程和体验目标 |

- 不新增阻断式角色确认步骤。

## 4. 产品理解约束

后端实现必须先读 `17-资深产品视角下的绘本创作流程理解.md`，再进入 schema、状态机和 API 实现。`17` 文档不是背景材料，而是实现正确性的产品约束。

### 4.1 产品北极星

后端实现最终要服务这个判断：

```text
用户是否觉得“这本绘本是我和 AI 一起做出来的，而且里面真的有我的故事”。
```

因此，后端不能只满足“接口能返回 200”。它必须支撑以下体验：

- AI 能复述用户想法，而不是只保存原始输入。
- AI 能提取专属素材，而不是让前端本地规则假装识别。
- 用户补充的素材能保存，并进入方向、大纲和最终生成。
- 用户选择的方向能被后端记录，并约束后续大纲和正式绘本生成。
- 高级画面偏好能真实进入生成任务。
- 生成和失败状态能恢复，用户不会丢失创作过程。

### 4.2 后端必须保护的三个用户感受

| 用户感受 | 后端需要提供的能力 |
| --- | --- |
| 被理解 | `understanding` 必须是结构化结果，包含 summary/goal/tone/scene/age_group |
| 有参与感 | `directions` 和 `selected_direction_id` 必须持久化，后续生成必须使用用户选择 |
| 有私人定制感 | `materials/personal_hook/material_ids` 必须进入 directions、outline、storybook generation |

### 4.3 后端不得把技术复杂度暴露给主流程

普通用户创作主流程不应该依赖或展示：

- provider。
- prompt schema。
- raw prompt。
- job type。
- seed。
- reference weight。
- model name。

这些信息可以存在于 `GenerationJob.input_json/output_json`、运营后台、日志或调试接口中，但面向前端主流程的 creation session response 必须使用用户语言：

- `understanding`
- `materials`
- `directions`
- `personal_hook`
- `outline`
- `visual_preferences`
- `next_action`

### 4.4 实现偏差红线

以下情况即使接口字段存在，也视为产品实现偏差：

- 后端不生成方向，只让前端继续用模板拼 3 个方向。
- 后端不提取素材，只保存用户输入文本。
- 用户 `PATCH /materials` 后，生成方向和大纲不受影响。
- `selected_direction_id` 只保存但不参与大纲和正式绘本生成。
- `visual_preferences` 可保存但不进入 `creation_storybook_generate` input。
- 生成完成后没有写回 `storybook_id/status=storybook_ready`，导致前端无法进入验收工作台。
- 失败信息只有技术错误，没有可恢复动作。
- `locked=true` 的专属素材只在语义上被使用，但没有让素材 `label` 原样进入成品标题、正文或插图描述，导致验收页无法确认私人定制感。
- provider prompt 禁止输出 schema 固定字段，例如 `provider`、`mode`、`quality_flags`，导致 prompt 与结构化输出契约互相冲突。
- 共创生成写入 `storybook_roles` 时使用非标准角色类型，应统一使用 `protagonist/supporting/peer/teacher/prop` 等既有枚举。

## 5. Skill 协作顺序

### 5.1 第一棒：database-schema-design

目标：决定共创会话如何落库，并确认 source of truth。

输入：

- `17-资深产品视角下的绘本创作流程理解.md`
- `15-专属故事共创后端接口契约.md`
- 现有 `Storybook`、`GenerationJob`、workspace、user 数据结构

必须产出：

- `storybook_creation_sessions` 表设计
- 字段类型和默认值
- JSON 字段边界
- 状态字段存储方式
- 和 `storybooks`、`generation_jobs` 的关系
- 索引设计
- migration 顺序
- 删除、放弃、完成后的生命周期规则

建议字段：

| 字段 | 要求 |
| --- | --- |
| `id` | 稳定 ID |
| `workspace_id` | 必须索引 |
| `created_by` | 必须索引 |
| `status` | 必须索引 |
| `quick_idea` | 原始输入 |
| `understanding_json` | AI 理解结果 |
| `materials_json` | AI 提取和用户补充素材 |
| `directions_json` | 故事方向 |
| `selected_direction_id` | 用户选择 |
| `outline_json` | 大纲 |
| `visual_preferences_json` | 画面偏好 |
| `storybook_id` | 最终绘本 |
| `last_job_id` | 最近生成任务 |
| `idempotency_key` | 防重复生成 |
| `requires_understanding_refresh` | 下游过期标记 |
| `requires_direction_refresh` | 下游过期标记 |
| `requires_outline_refresh` | 下游过期标记 |
| `created_at/updated_at` | 审计和恢复 |

完成标准：

- P0 8 个接口都能通过该 schema 完成读写。
- 前端刷新恢复不依赖 localStorage 作为主存储。
- `session_id + idempotency_key` 能防重复创建 Storybook。
- 可以按 `workspace_id/created_by/status/updated_at` 找到最近未完成会话。
- `understanding/materials/directions/outline/visual_preferences` 都有后端 source of truth。

交接给下一棒：

- 数据字段清单。
- 字段默认值。
- 哪些字段是状态机控制字段。
- 哪些字段由 worker 写回。

### 5.2 第二棒：workflow-state-machine-design

目标：把共创会话状态集中定义，避免状态逻辑散落在 handler、worker 和前端里。

输入：

- database-schema-design 的表结构
- `15` 文档中的状态机

必须产出：

- 状态列表
- 允许的状态流转
- 每个接口的 guard
- 每个状态变化的副作用
- 失败、重试、放弃、重复提交处理
- 修改想法、素材、方向、大纲后的下游过期规则

状态列表：

```text
draft
understanding_ready
directions_ready
direction_selected
outline_ready
generating
storybook_ready
failed
abandoned
```

关键 guard：

| 动作 | 必要状态 | 不满足时 |
| --- | --- | --- |
| 选择方向 | `directions_ready` | `409 state_conflict` |
| 生成大纲 | `direction_selected` | `409 state_conflict` |
| 一键生成 | `outline_ready` | `409 state_conflict` |
| 修改素材 | 非 `generating/storybook_ready/abandoned` | `409 state_conflict` |
| 放弃会话 | 非 `storybook_ready/abandoned` | `409 state_conflict` 或幂等返回 |

关键副作用：

- 修改 `quick_idea`：清理 directions、selected direction、outline，标记理解/方向/大纲过期。
- 修改 materials：标记方向/大纲过期。
- 重新生成 directions：清理 selected direction 和 outline。
- 选择 direction：状态进入 `direction_selected`。
- 生成 outline：状态进入 `outline_ready`。
- 生成 Storybook：状态进入 `generating`，写入 `storybook_id/last_job_id/idempotency_key`。
- job 成功：状态进入 `storybook_ready`。
- job 失败：状态进入 `failed`，保留 `storybook_id/last_job_id`。

完成标准：

- 每个 P0 接口都有明确状态前置条件。
- 不存在“未选方向生成大纲”。
- 不存在“重复点击生成创建多本绘本”。
- 失败后有明确重试路径。

交接给下一棒：

- 每个接口对应的 allowed states。
- 每个接口成功后的 target state。
- 每个失败场景的错误码。

### 5.3 第三棒：api-contract-design

目标：把 `15` 文档固化为最终后端接口契约。

输入：

- database-schema-design 输出
- workflow-state-machine-design 输出
- `15-专属故事共创后端接口契约.md`

必须产出：

- P0 8 个接口最终 request/response
- P1/P2 接口是否暂不实现的明确说明
- 统一错误 envelope
- 权限规则
- 字段命名规范
- 是否需要同步更新 `03-后端接口契约.md`

必须检查：

- 所有成功响应都包在 `{ "data": ... }`。
- 列表响应包含 `meta.total/limit/offset/has_more`。
- 写接口返回足够前端更新 UI 的字段，至少包括 `id/status/updated_at`。
- `PATCH /materials` 使用 `operations[]`，不是模糊全量替换。
- `POST /storybook:generate` 请求包含 `idempotency_key`。
- `PATCH /visual-preferences` 是 P0。
- 错误码可被前端稳定判断。

完成标准：

- 前端可以根据接口文档写 client，不需要猜字段。
- 后端可以根据接口文档写 handler，不需要回头问产品。
- 状态 guard 和错误模型体现在接口契约中。

交接给下一棒：

- 最终 P0 API 表。
- request/response 类型。
- 需要接入异步任务的接口。

### 5.4 第四棒：job-queue-design

目标：设计一键生成正式绘本的异步任务，并确认它和现有 GenerationJob 兼容。

输入：

- api-contract-design 输出
- workflow-state-machine-design 输出
- `05-异步任务与生成队列设计.md`

必须产出：

- `creation_storybook_generate` job type
- 可选的 `creation_understanding / creation_directions / creation_outline` job type
- job input_json
- job output_json
- worker 执行顺序
- 幂等和去重规则
- 失败和重试规则
- 用户可见进度
- operator 排查信息

P0 异步边界：

| 能力 | P0 方式 |
| --- | --- |
| 创建会话与理解 | 同步返回 |
| 生成方向 | 同步返回 |
| 生成大纲 | 同步返回 |
| 一键生成正式绘本 | 异步返回 `job_id` |

`creation_storybook_generate` worker 顺序：

```text
读取 creation session
  -> 校验状态和 idempotency
  -> 创建或复用 Storybook
  -> 生成角色和道具
  -> 生成分页文本与插图提示词
  -> 根据 include_images 排队封面和分页插图
  -> 写回 storybook_id/status=storybook_ready
```

关键幂等规则：

- 以 `session_id + idempotency_key` 去重。
- 重复提交返回已有 `storybook_id/job_id`。
- worker 重试不得重复创建 Storybook。
- job 失败后保留半成品 Storybook，便于重试补齐。

完成标准：

- 重复点击不会创建多本。
- 网络超时重试不会创建多本。
- worker 失败后前端能看到失败原因。
- 重试路径明确。

交接给下一棒：

- job type 和 payload。
- worker 写回字段。
- 前端轮询方式。

### 5.5 第五棒：full-stack-design-sync

目标：把产品流程、数据库、API、异步任务和前端 UI 做最终对齐。

输入：

- database-schema-design 输出
- workflow-state-machine-design 输出
- api-contract-design 输出
- job-queue-design 输出
- `17-资深产品视角下的绘本创作流程理解.md`
- `14` UI 流程文档
- `15` 接口文档

必须产出：

- 主流程映射表
- 数据支持检查
- API 支持检查
- 前端状态支持检查
- 不一致项
- 推荐调整
- 冻结版 phase-1 blueprint

主流程映射模板：

| 用户动作 | UI 状态 | API | 数据写入 | 状态变化 | 下一步 |
| --- | --- | --- | --- | --- | --- |
| 输入一句故事想法 | 想法页 | `POST /storybook-creation-sessions` | session + understanding + materials | `understanding_ready` | 生成方向 |
| 补充素材 | 方向页 | `PATCH /materials` | materials_json | 标记方向/大纲过期 | 刷新方向 |
| 换一批方向 | 方向页 | `POST /directions:generate` | directions_json | `directions_ready` | 选择方向 |
| 选择方向 | 方向页 | `POST /direction` | selected_direction_id | `direction_selected` | 生成大纲 |
| 生成大纲 | 大纲页 | `POST /outline:generate` | outline_json | `outline_ready` | 生成整本 |
| 调整画面 | 生成页 | `PATCH /visual-preferences` | visual_preferences_json | 保持 `outline_ready` | 一键生成 |
| 一键生成 | 生成页 | `POST /storybook:generate` | storybook_id + job_id | `generating` | 轮询 |
| 生成成功 | 生成页 | `GET /session` | 读取 storybook_id | `storybook_ready` | 验收工作台 |

完成标准：

- 没有 UI 状态只能靠前端假数据支撑。
- 没有 API 写入无法从数据库恢复。
- 没有状态流转只能靠前端猜。
- 没有异步任务完成后不知道写回哪里。
- 没有违背 `17` 中“被理解、参与感、私人定制感”的核心产品判断。

## 6. 后端实现阶段

建议分 5 个实现阶段，避免一次性大改。

### 阶段 1：Schema + Migration

实现内容：

- 新增 `storybook_creation_sessions` 表。
- 增加必要索引。
- 增加 SeaORM entity/model。
- 增加基础枚举和 JSON 类型。

验收：

- migration 可重复执行。
- 数据库能创建、查询、更新 session。
- 不影响现有 Storybook、GenerationJob 流程。

### 阶段 2：Session 基础接口

实现内容：

- `POST /storybook-creation-sessions`
- `GET /storybook-creation-sessions/:id`
- 基础权限检查。
- 初始理解和素材可以先接 mock/provider。

验收：

- 输入一句想法后返回 session。
- 返回包含 `understanding/materials/visual_preferences/status`。
- 刷新后能读取完整 session。

### 阶段 3：素材、方向、大纲

实现内容：

- `PATCH /materials`
- `POST /directions:generate`
- `POST /direction`
- `POST /outline:generate`
- `PATCH /visual-preferences`

验收：

- 素材补充使用 `operations[]`。
- 方向由后端返回，不再依赖前端模板。
- 选择方向被后端记录。
- 大纲基于已选方向生成。
- 画面偏好保存后能在 session 读取。

### 阶段 4：一键生成异步任务

实现内容：

- `POST /storybook:generate`
- `creation_storybook_generate` job type。
- 幂等保护。
- worker 创建或复用 Storybook。
- 写回 `storybook_id/last_job_id/status`。

验收：

- 重复调用不会创建多本。
- 失败能进入 `failed`。
- 成功进入 `storybook_ready`。
- 生成后能打开现有验收工作台。

### 阶段 5：前端接入和旧逻辑替换

实现内容：

- 前端接新 P0 API。
- 移除或降级前端 `materialLabelsFor()` 规则逻辑。
- 移除或降级前端 `directionsFor()` 模板逻辑。
- localStorage 只保留弱网兜底，主恢复读后端 session。

验收：

- 刷新页面后能恢复。
- 换浏览器登录后能继续上次 session。
- 高级画面设置真实进入后端。
- 一键生成后能进入验收工作台。

## 7. 三层验收机制

### 7.1 第一层：api-contract-design 验接口

负责回答：

```text
接口有没有按契约做对？
```

验收范围：

- P0 8 个接口是否全部实现。
- 请求字段是否符合 `15`。
- 响应字段是否符合 `15`。
- 写接口是否返回 `id/status/updated_at`。
- 错误 envelope 是否统一。
- `PATCH /materials` 是否只接受 `operations[]`。
- `POST /storybook:generate` 是否要求 `idempotency_key`。
- 权限错误、状态错误、字段错误是否能区分。

阻断项：

- 任一 P0 接口缺失。
- 成功响应没有 `{ "data": ... }`。
- 错误响应不是统一 envelope。
- 生成接口没有幂等保护。
- 素材接口仍采用模糊全量替换语义。

### 7.2 第二层：workflow-state-machine-design 验状态

负责回答：

```text
状态流转有没有漏洞？
```

验收范围：

- 未选方向不能生成大纲。
- 未生成大纲不能一键生成绘本。
- 修改想法后，下游方向和大纲是否过期。
- 修改素材后，方向和大纲是否过期。
- 重新生成方向后，旧选择和旧大纲是否清理。
- `generating` 重复提交是否返回已有 job/storybook。
- `failed` 是否能重试。
- `storybook_ready` 是否不会被隐式覆盖。
- `abandoned` 后是否不能继续生成。

阻断项：

- 任一非法状态操作能成功。
- 失败后没有恢复路径。
- 重复提交会创建重复 Storybook。
- 状态只存在前端，数据库无法恢复。

### 7.3 第三层：full-stack-design-sync 验端到端

负责回答：

```text
产品流程、前端、API、数据库、异步任务是否真的一致？
```

验收范围：

- 是否符合 `17` 中的产品北极星。
- 想法页是否由后端返回理解和素材。
- 方向页是否由后端返回 3 个方向和 personal_hook。
- 补充素材是否进入后端 session。
- 选择方向是否写入后端。
- 大纲是否基于方向和素材生成。
- 画面偏好是否进入后端并传给生成任务。
- 一键生成是否创建正式 Storybook。
- 生成完成后是否能打开验收工作台。
- 刷新、失败、重试、继续编辑是否跑通。

阻断项：

- 后端实现让用户感受不到“AI 理解我、我参与选择、我的素材被使用”。
- 前端仍依赖本地模板作为主方向来源。
- 前端仍依赖本地素材识别作为主来源。
- session 无法从后端恢复。
- job 成功后 session 没有写回 `storybook_id/status`。
- 生成结果没有进入现有 Storybook 详情页。

## 8. 可选体验验收

后端和前端接通后，再做一次体验复验。

### 8.1 frontend-reviewer

检查：

- 接入新接口后页面是否变乱。
- loading、empty、error、success 状态是否清楚。
- 按钮是否重新拥挤。
- 移动端文字是否溢出。
- 生成失败和重试是否可理解。

### 8.2 ux-designer

检查：

- 用户是否仍然能一句话开始。
- 用户是否能感到“AI 理解了我”。
- 用户是否知道自己参与了方向选择。
- 用户是否能确认专属素材进入故事。
- 高级设置是否保持低干扰。
- 验收是否仍然是“只改不满意”，不是逐页打卡。

## 9. 最终验收清单

### 9.1 产品理解验收

- [ ] 后端实现前已阅读 `17-资深产品视角下的绘本创作流程理解.md`。
- [ ] 后端返回 `understanding`，而不是只保存 `quick_idea`。
- [ ] 后端返回 `materials`，并支持用户补充素材。
- [ ] 后端返回 3 个有差异的 `directions`。
- [ ] 每个 direction 包含 `personal_hook`。
- [ ] `selected_direction_id` 参与 outline 和 storybook generation。
- [ ] locked 素材进入 directions、outline 或 generation input。
- [ ] 主流程 response 不要求前端展示 provider、prompt schema、raw prompt、job type。

### 9.2 接口验收

- [ ] P0 8 个接口实现。
- [ ] 所有成功响应使用 `{ "data": ... }`。
- [ ] 所有错误响应使用 `{ "error": { "code", "message", "field" } }`。
- [ ] `PATCH /materials` 使用 `operations[]`。
- [ ] `POST /storybook:generate` 要求 `idempotency_key`。
- [ ] `PATCH /visual-preferences` 是 P0 并真实保存。

### 9.3 状态验收

- [x] session 状态可从数据库恢复。
- [x] 非法状态操作返回 `409 state_conflict`。
- [x] 修改想法会清理下游结果。
- [x] 修改素材会标记方向和大纲过期。
- [x] 重复生成不会创建多本 Storybook。
- [x] 失败后可重试。
- [x] 完成后不会被隐式覆盖。

### 9.4 异步任务验收

- [x] `creation_storybook_generate` job type 实现。
- [x] job input 使用稳定引用。
- [x] job 成功写回 session。
- [x] job 失败写回 `failed/last_job_id`。
- [x] worker 重试幂等。
- [x] 前端能轮询进度。

### 9.5 前端闭环验收

- [ ] 想法页调用后端创建 session。
- [ ] 方向页展示后端素材和方向。
- [ ] 素材补充写入后端。
- [ ] 方向选择写入后端。
- [ ] 大纲来自后端。
- [ ] 画面偏好写入后端。
- [ ] 一键生成后进入验收工作台。
- [ ] 刷新后从后端恢复 session。
