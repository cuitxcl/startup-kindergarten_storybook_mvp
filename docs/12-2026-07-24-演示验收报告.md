# 2026-07-24 演示验收报告

## 1. 结论

Kindleaf 当前已经达到 **本地真实 API + PostgreSQL 可演示闭环** 阶段。按“先不用生产化”的口径，整体完成度约为 **95%**。

这个 95% 指的是：老师和园所可以通过真实后端 API 跑通核心产品路径，数据持久化、权限、状态机、生成任务、导出、分享、市场复用、用户/空间存储限额和基础运营检查都已经具备演示能力；单儿童定制与批量定制都已被 API smoke 和浏览器 UI smoke 覆盖。它不等于生产上线完成。

## 3. 当前后端状态

后端已经从早期大 controller / 大 repository 逐步转向领域拆分：

- `application/`：承接用例编排，例如 workspaces、operator、generation、storybooks。
- `repositories/`：承接数据库读写、分页、状态更新和业务查询。
- `services/`：承接生成 provider、storage、PDF 等底层能力。

最近拆分已经覆盖：

- 生成成本与预算：`generation_costs.rs`
- 图片生成任务：`generation_image_tasks.rs`
- 任务队列状态：`generation_jobs.rs`
- 生成结果写回：`generation_writeback.rs`
- 存储空间限额：`storage_quota.rs`
- 绘本查询、创建、编辑、定制、状态规则：`storybook_queries.rs`、`storybook_factory.rs`、`storybook_editing.rs`、`storybook_customization.rs`、`storybook_rules.rs`
- DeepSeek、Seedream、mock provider、输出校验、隐私脱敏、配置摘要：`generation_*_provider.rs` 等 service 文件

这说明架构已经在向“领域化 + application 用例层”转化，不再是单文件堆代码。

## 4. 存储限额状态

用户提出“每个用户有一定的存储空间限额”后，当前实现口径已经落到 **用户个人额度 + workspace 额度**：

- 当前登录用户个人内容默认 200MB。
- 个人空间默认 200MB。
- 园所空间默认 5GB。
- 用户额度可用环境变量覆盖：`KINDLEAF_USER_STORAGE_QUOTA_BYTES`。
- 可用环境变量统一覆盖：`KINDLEAF_WORKSPACE_STORAGE_QUOTA_BYTES`。
- 后端会按任务发起人统计个人已用容量：用户在个人空间或园所空间发起且成功落盘的图片和 PDF 都会计入个人额度。
- 任务发起人归属字段 `created_by` 只用于后端容量统计和运营分析，不作为前端 API 字段返回；API smoke 已验证生成任务、导出任务和公开分享导出响应均不会暴露该字段。
- 后端会按当前空间下成功生成的图片和成功导出的 PDF 文件大小统计已用容量。
- 图片生成和登录态 PDF 导出在写入成功状态前检查空间容量和发起人的用户个人总额度；公开分享导出没有登录用户，只计入 workspace 容量。
- 超限时返回 `storage_quota_exceeded`，阻止任务继续成功。
- 前端 API client 已有 `/api/auth/storage-quota` 映射，工作台容量卡会展示“我的容量”。
- 前端已有 `/api/workspaces/{workspace_id}/storage-quota` 的 client 映射和工作台展示入口。
- 平台运营 storage 面板已展示“用户个人限额 / 个人空间限额 / 园所空间限额 / 容量预警线”，UI smoke 已纳入这些文案的可见性断言。

下一步如果要更精细，可以继续升级为“用户套餐额度 + 园所套餐额度 + 对象存储生命周期”的生产模型；但就当前演示版，用户个人额度和园所共享额度已经能表达容量边界。

## 7. 为什么现在看起来文件很多

当前 `git status` 里会看到大量 `.tmp/`、`server/tmp/`、`frontend/dist/` 下的删除记录。这不是功能倒退，而是仓库清理：

- `.tmp/` 是 smoke 测试日志和临时数据库导出。
- `server/tmp/` 是本地生成的 PDF 和图片。
- `frontend/dist/` 是前端构建产物。

这些文件已经加入 `.gitignore`，并通过 `git rm --cached` 从 git 跟踪中移除，本地文件不会因此被删除。这个动作是为了让仓库只保留源码、脚本和文档，不再提交运行产物。

## 8. 下一步建议

为了快速进入“可交付演示版”，建议只做四件事：

1. 保持当前领域架构拆分成果，继续避免 controller/application/repository 再次膨胀。
2. 阶段性交接前继续运行 `CHECK_SMART_RUN_FULL=true ./scripts/check-smart.sh auto`，固定当前 API + UI 通过状态。
3. 如需真实图片演示，配置 `SEEDREAM_API_KEY` 或 `ARK_API_KEY` 后运行真实 Seedream smoke。
4. 将当前变更按“源码变更 + 文档 + 生成物清理”整理成一次提交。

按这个口径，当前不是“越来越远”，而是已经越过主要功能实现期，进入验收、清理和真实 provider 配置期。
